# PRS Apps — agent guide

Internal tool hub for **Power & Rubber Supply**, deployed at **prstech.app**. Despite the repo name (`it-asset-tracker`, its original single purpose), it's now a multi-app hub. Read this before making changes.

## Build approval required (IMPORTANT — read first)

**Never build anything in the app without Porter's explicit approval, per request.** Before writing code for any feature, page, schema/infra change, or behavior change — including follow-on ideas and improvements you discover mid-task — first present the idea: what it does, why, the approach, and what it touches (routes, tables, migrations, worker, external services). Then **stop and wait for approval**. Notes:

- A request to investigate, analyze, or spec something is **not** approval to build it.
- Approval of one thing does not extend to the next idea it spawns — propose each separately.
- Directly requested small fixes (a bug being pointed at, a typo, a copy change) don't need a separate proposal — the request itself is the approval.

## Keep this guide current

When a change alters something this file describes — architecture, a convention, the app list, environment variables, commands, or a new gotcha — update this file **as part of the same change**, and mention that you did. Don't log routine changes here: this is a durable map loaded every session, not a changelog. Keep it lean and high-signal.

## Changelog

Record **notable** changes (new features, schema/infra changes, behavior changes, new gotchas) in `CHANGELOG.md`, newest first. Every entry requires a **date heading** (`## YYYY-MM-DD`) and a **one-to-two-line bullet** describing the change. Add to the existing date section if it's the same day, otherwise start a new one. Keep entries terse — git history holds the fine detail; skip trivial/routine changes.

## Stack & deploy

- **Next.js (App Router)** + **React**, all UI in plain inline styles (no Tailwind/CSS modules in app code).
- **Supabase** — Postgres + Auth + Storage. Client via `src/lib/supabase.js` (`createClient()`), server/service-role via `src/lib/supabaseAdmin.js` (`createAdminClient()` — never import into a client component).
- **Vercel** — pushing to `main` auto-deploys to production. `vercel.json` defines daily crons (Graph subscription renewal, batch reminders).
- **Canonical domain is `https://www.prstech.app`.** The apex `prstech.app` 307-redirects to `www`. Anything that must not be redirected (Graph webhooks, external callers) must use the `www` host.

## The apps

Each app is gated per-user. Current apps: **IT Tracker** (`tracker`), **Material Calculator** (`calculator`), **Help Desk** (`helpdesk`), **Price Update Processor** (`priceupdates`, being built in phases — see `price-update-processor/build-spec.md`), **Daily Ops** (`dailyops`, planned). ## Auth, roles & per-app access (important, easy to get wrong)

- `src/lib/useRole.js` — the `useRole()` hook exposes `role`, `isAdmin`, `user`, `loading`, and **`hasAccess(appId)`** = `isAdmin || appAccess.includes(appId)`. `app_access` is a **JSONB array of app-id strings** on `profiles` (not an object of booleans). **Admins always see every app.**
- **Registering a new app touches THREE files** — keep them in sync:
  1. `src/components/navigation.js` — the `tools` array (top-nav dropdowns).
  2. `src/app/page.js` — the home-page tile grid.
  3. `src/app/admin/page.js` — the `allApps` array (admin access checkboxes).
- Every app page guards itself: `if (!loading && !hasAccess('<appId>')) router.push('/')`. For multi-page apps, do it once in the app's `layout.js` (see `src/app/helpdesk/layout.js`).
- `src/proxy.js` (Next 16's renamed middleware convention) redirects logged-out users to `/login` for everything **except** the public webhook API routes listed in its `matcher` (Graph notify/subscribe, inbound email). If you add a public/externally-called API route, add it to that exclusion or it will 307-redirect and break.

## Data access & RLS

- Row-Level Security is **on** for every table; policies target the `authenticated` role. `is_agent()` = `profiles.role = 'admin'`.
- Client components read/write through the anon client and are constrained by RLS.
- **Server API routes that act without a user session** (inbound email, notifications) use the **service-role** client, which bypasses RLS by design. Guard them yourself (shared token / bearer / Graph `clientState`).

## Help Desk (main recent build)

- Routes under `src/app/helpdesk/`: dashboard (`/helpdesk`), ticket queue (`/tickets`), new (`/tickets/new`, agent logs on behalf of a requester), detail (`/tickets/[id]`), KB (`/kb`, `/kb/[slug]`, `/kb/manage`).
- Shared helpers in `src/lib/helpdesk.js` (status/priority/SLA/category metadata + formatters) and `src/lib/kb.js` (slug + minimal markdown).
- **Status vs. State:** `status` is the workflow (`open→in_progress→waiting→resolved→closed`); SLA **state** (`overdue/due_today/on_time`) is *derived* (SQL `ticket_list_view` + JS `slaState()`), never stored.
- **SLA timers** come from the `sla_policies` table by priority, stamped on insert and recalculated on priority change (DB triggers). Change the windows by editing that table, not code.
- **Categories** are a `category` text field; the shared list + labels live in `CATEGORY_OPTIONS`/`categoryLabel` in `src/lib/helpdesk.js`.
- **Email (Microsoft Graph, not Power Automate):** inbound via Graph push subscriptions → `POST /api/helpdesk/graph-notify` creates a ticket; `POST /api/helpdesk/graph-subscribe` creates/renews subscriptions (daily Vercel cron). Outbound sends as `it@` via Graph (`/api/helpdesk/notify`, Power Automate fallback retained). The mailbox→queue is carried in the subscription `clientState` (`<secret>|<queue>`), because Graph's notification `resource` uses an internal id, not the email. `it@` → Help Desk ticket (general); **`priceupdate@` → a Price Update Processor batch, not a ticket** (Phase 6a — `createEmailBatch()` in `src/lib/emailBatch.js`; the old `price_update` ticket path is gone). Full setup: `docs/email-setup-graph.md`.

## IT Tracker (asset management)

Being fleshed out in stages (see `CHANGELOG.md`; **Stages 0–5 done**, label printing to come).

- Routes under `src/app/tracker/`: dashboard (`/tracker`), assets list (`/tracker/assets`, with a Group-by None/Employee/Location control), employees (`/tracker/employees` + detail `/tracker/employees/[id]`), racks (`/tracker/racks` + detail `/tracker/racks/[id]` with the U-position visualization), locations (`/tracker/locations` + detail `/tracker/locations/[id]` managing rooms), licenses, budget, history. Guarded once in `src/app/tracker/layout.js` via `hasAccess('tracker')`. Editing an employee happens on the detail page; the list only adds.
- **Racks:** a rack has a `u_height` (size in U). A device is a normal rackable asset (`type` with `rackable: true`) carrying `rack_id` + `u_position` + `u_height` + `watts`; `rack_id` set with `u_position` NULL = **off-rack** (in the room, not mounted). Rack total power is derived by summing device `watts` (never stored). The detail page renders a to-scale U grid (`ROW_PX` px per U) styled as a physical rack (metal frame + mounting rails); mounted devices render as type-specific faceplates via `src/components/RackDeviceFace.js` (`faceCategory()` maps type → network/server/storage/ups/monitor/other). Placement/overlap validation lives in `rackPlacementError()`.
- **Rack audits (Stage 5):** starting an audit (`rack_audits`) snapshots the mounted devices into `rack_audit_items` (name/type/expected slot copied so history survives asset changes). Conducted at `/tracker/racks/[id]/audits/[auditId]`: mark Present/Moved/Missing, log unexpected "extra" devices, record condition + notes, Complete (or Discard). Completed audits are read-only. A "discrepancy" (`isDiscrepancy()` in `lib/tracker.js`) = missing/moved/extra or a non-OK condition. Findings can be **reconciled** into the live data: "extra" → Create asset (opens `AssetModal` with its `defaults` prop prefilled, then links the new asset back to the item); "moved" → Apply move (repositions the real asset); "missing" → Remove from rack (detaches `rack_id`/`u_position`).
- Shared helpers live in **`src/lib/tracker.js`** (statuses, categories, asset **types** with `computer` + `rackable` flags via `isComputerType()`/`isRackableType()`, status colors, `formatCurrency`/`formatDate`, straight-line depreciation, `rackPlacementError()` for rack fit/overlap checks) — reuse these instead of re-declaring inline. `type` drives which detail fields `AssetModal`/`AssetDetail` show (computer specs vs. management URL). **Rack-mountability is a separate per-asset `rack_mountable` boolean** (a checkbox), NOT inferred from type — `isRackableType()` is only the suggested checkbox default when picking a type on a new asset.
- **Schema:** tracker DDL is committed across numbered migrations starting at `supabase/05_tracker_schema.sql` (the tables predated it and were hand-made, so migrations are idempotent/additive). Tables: `assets`, `employees` (company directory, distinct from app-login `profiles`; `first_name`/`last_name` with `full_name` as the app-written combined value), `locations` → `rooms` (two-level hierarchy; employees/assets/racks carry `location_id` + optional `room_id`), `racks`, plus `licenses/budgets/purchases/subscriptions/audit_log`. Later migrations: `06` (employee name split), `07` (location→room hierarchy), `08` (`assets.rack_mountable` flag), `09` (`rack_audits` + `rack_audit_items`). **Gotcha:** `assets.id` is a **`bigint`** (the assets table was hand-made before the migrations), whereas the migration-created tracker tables (`employees`, `locations`, `rooms`, `racks`, `rack_audits`) use **`uuid`** PKs. So a FK *referencing* `assets(id)` must be `bigint` (see `rack_audit_items.asset_id`), not `uuid`.
- **Asset IDs:** every asset gets an immutable `asset_tag` = `PRS-#####` (global `asset_tag_seq`, auto-assigned via column default). This ID is also the printed asset-tag label.
- **Rack membership:** a `rack_mountable` device with `rack_id` + `u_position` is mounted at that U; `rack_id` set with `u_position` NULL = "off-rack" (in the room, not physically racked). Placement is validated (fit + no overlap) via `rackPlacementError()`. Rack total power is derived by summing device `watts`, not stored.
- `assigned_employee_id` (FK → `employees`) is the real assignment; the legacy free-text `assigned_to` is retained until Stage 1 migrates the UI.

## Price Update Processor (`priceupdates`) — in progress

Replaces the retired Invoice Processor's price-update duty; first app to integrate with Prophet 21 (P21). Full brief + phased plan in `price-update-processor/build-spec.md`. **Phases 1–7 complete** (5.5 file library, 6a email intake, 6b auto-parse on arrival + PDF split view, 7 polish/vendor CRUD); Phase 8 is an approved-per-item backlog.

- Vendors email price/cost updates to `priceupdate@`. The app is a pipeline: **intake → parse → match against a P21 item mirror → review/approve with guardrails → export a P21-ready import file**. A human loads the file into P21's import tool and marks it applied — **v1 does not write to P21**.
- Routes under `src/app/priceupdates/`: dashboard (`/priceupdates`), batch queue (`/priceupdates/batches` + detail `/priceupdates/batches/[id]`, and the column-mapping UI `/priceupdates/batches/[id]/map`), vendors, files (`/priceupdates/files`), settings. Guarded once in `src/app/priceupdates/layout.js` via `hasAccess('priceupdates')` (Help Desk-style icon rail). App id defaults **off** except the owner.
- **Batch lifecycle:** `received → parsing → needs_review → approved → exported → applied` (+ `failed`, `archived`). Status is the workflow; the queue also shows a **derived attention pill** (unmatched/flagged/awaiting-load) computed from line counts — same status-vs-derived-state idea as Help Desk SLA pills. Helper: `attentionPill()` in `src/lib/priceupdates.js` (status/source/match/flag meta + formatters live there too). **Pre-approval batches (received/parsing/needs_review/failed) can be deleted** from the detail page: removes lines/files/exports (FK cascade + storage objects by path) and the library copies auto-archived from the batch; manually-linked library files are only unlinked (`batch_id` FK nulls). **Files are optional at creation** — a batch can start as a scheduled placeholder (notification received, vendor file not yet released): it shows an "Awaiting file" attention pill (`file_count` from a `pu_batch_files(count)` embed) and files are added later via "+ Add files" on the detail Files card; both paths share `uploadBatchFiles()` in `src/lib/priceupdatesParse.js` (upload + `pu_batch_files` row + library archive).
- **Parsing (Phase 2):** server route `POST /api/priceupdates/parse-file` (Bearer-auth + `priceupdates` access check; SheetJS/`xlsx` reads .xlsx/.xls/.csv from `price-files` via the service role) returns raw 2-D rows, **windowed 20k rows per response** (Vercel's ~4.5MB response cap — `offset` param; `fetchParsedSheets` pages and stitches, so callers always get complete sheets and files >20k rows parse fully). Pure transforms live in `src/lib/priceupdates.js` (`parseNumber`, `parseDateish`, `buildLinesFromRows(rows, config)` — multiplier / discount-%-off-list / strip-prefix; blank≠zero, skips+counts no-price lines; keeps the untouched row in `pu_lines.raw`). Client-side DB writes go through `src/lib/priceupdatesParse.js` (`fetchParsedSheets`, `applyParse`). A saved **parse profile** (`pu_parse_profiles.config` = `{sheet, header_row, skip_rows, columns:{field→colIndex}, transforms}`) lets a known vendor's file **auto-parse in one click**; unknown files walk through the mapping UI once and the profile sticks.
- **P21 integration (Phase 3, read-only):** two generic, app-agnostic server-only clients — reuse them for future P21 apps. **`src/lib/p21sql.js`** (preferred): Epicor's hosted read-only **SQL Server replica** (`mssql`, `P21_SQL_*` env). **Gotcha: the replica is IP-allowlisted by Epicor** — reachable from the office network, **not from Vercel's egress** (every attempt from production 502s in ~16s), so anything that talks to it must run on-prem. **`src/lib/p21.js`** (fallback): the OData client (token cache/refresh, retry/backoff, paged `$top/$skip` GET) — on our instance the gateway currently **denies all OData data reads (401)** even with a registered consumer key, pending an Epicor-side grant; token + catalog work. View/field names are shared between both paths and env-overridable (confirmed against the replica). **Mirror syncs run on the on-prem worker** (`worker/sync-worker.mjs`, self-contained Node script on an office server — see `worker/README.md`): a nightly full sync via Task Scheduler (`--once`, the backstop) plus a `--watch` loop that heartbeats to `pu_settings` (`worker_heartbeat_at`/`worker_last_result`, migration `14` — drives the Settings online pill) and drains the **`pu_sync_requests` queue** (migration `15`): creating a batch enqueues a **supplier-scoped** sync for that vendor (fire-and-forget in `NewBatchModal`; batch detail shows "P21 data synced Xm ago"), Settings "Sync now" enqueues an all-suppliers row and polls the request for its result. Scoped-by-default matters: the supplier list will grow to ~150+, so on-demand full syncs won't scale — per-supplier stays seconds-fast. `POST/GET /api/p21/sync-items` (Bearer: `CRON_SECRET` or a logged-in `priceupdates` user; excluded in `proxy.js`) remains as the in-app fallback — Settings "Test connection" exercises it, and it would work again if Epicor ever allowlists Vercel; the old nightly Vercel cron for it was removed from `vercel.json`. Sync upserts item + supplier-cost rows into `p21_item_mirror` (verified live: 71.5k rows across Gates/ContiTech/Parker). **Writing to P21 is out of scope for v1** — the export file is the write path.
- **Matching (Phase 3, revised in Phase 5.1):** `POST /api/priceupdates/match` (Bearer-auth) normalizes each line's `vendor_item_no` and resolves it in order: **(0) `pu_item_aliases` match memory** (a resolution confirmed on a previous batch for this vendor wins outright → `matched`), then the mirror scoped to the vendor's `p21_supplier_id` two ways: (a) `supplier_part_no`, and (b) `p21_item_id` with the vendor's **`p21_item_prefix`** stripped (P21 ids are `"<prefix><space><vendor part>"`, e.g. `GAT QD12/8V71.00`). 1 distinct hit → `matched`; 0 → `unmatched`; >1 → `ambiguous` **but the closest candidate is auto-picked** (`pickBestCandidate()`: exact cross-ref > exact prefix-bridge id > has-prefix > has-cost; deterministic tie-breaks) and written with real old cost/list/Δ%/guardrail flag, included by default — the reviewer skims the Ambiguous tab, never resolves line-by-line. **Approving confirms the picks**: they're upserted into `pu_item_aliases` (source `review`; manual search-modal fixes write source `manual`, clearing deletes) and promoted to `matched` so they export. `matched_count` = every line carrying a pick (incl. auto-picked ambiguous); `flagged_count` = **matched-only** guardrail hits, same as the Flagged tab (ambiguous never mixes into Flagged). Flags come from `pu_settings` via `computeFlag()` (priority: large_increase > cost_over_list > decrease > ok). Runs after parse + via a **Re-run matching** button; bulk-applied through the `pu_apply_matches(jsonb)` SQL fn (leaves the reviewer's `include` flag untouched). Pure helpers (`normalizePart`, `costChangePct`, `computeFlag`, `pickBestCandidate`) live in `src/lib/priceupdates.js`.
- **Review/approve (Phase 4):** the batch detail page is a two-pane review screen (Help Desk-ticket style) — left: editable line grid with All/Flagged/Ambiguous/Unmatched/Excluded tabs, **server-side pagination** (100/page — never load a whole batch; PostgREST caps un-ranged selects at 1000), inline edit of `new_cost`/`new_list`, a mirror-backed **item-search modal** to fix unmatched/ambiguous lines (scoped to the vendor's `p21_supplier_id`), per-line + bulk include/exclude; right: properties sidebar (vendor/status/counts, files + parse actions, timeline, Approve). **Include defaults follow the match outcome:** the match route auto-excludes unmatched lines, re-includes a line that transitions unmatched→matched/ambiguous while excluded, and otherwise never touches the reviewer's include choice on re-runs; fixing/clearing a match in the UI applies the same defaults. **Approve** is gated on zero *included* ambiguous lines **without a pick** (re-verified server-side at click; auto-picked ambiguous don't block — approving confirms them into `pu_item_aliases` and promotes them to `matched`), stamps `approved_by/at` + `reviewed_by`, appends an activity line to `notes`, status → `approved`. Editing locks once a batch leaves `needs_review`. Edits recompute Δ%/flag client-side via the shared `costChangePct`/`computeFlag` and keep `matched_count`/`flagged_count` in sync (same definitions as the queue pills).
- **Export (Phase 5):** `POST /api/priceupdates/export` (Bearer-auth, same guard as parse-file) emits the P21 import file from **included + matched** lines only — a tab-delimited **.txt, CRLF**, header row, columns in the fixed order `Item ID, List Price, New Cost, Supplier ID` (P21's import tool reads columns **by position, not header name** — never reorder). Template sample: `price-update-processor/samples/GAT2026.txt` (gitignored — samples hold real vendor pricing); file name = `<vendor p21_item_prefix><effective-date year>.txt` (e.g. `GAT2026.txt`). **P21 treats a blank cell as "no change"**, so cost-only/list-only lines leave the other price column empty (never restate the mirror value). File goes to `price-files` under `exports/<batchId>/`, a `pu_exports` row records it, status → `exported` (regenerate allowed while `exported`). "Mark applied in P21" and "Archive batch" are client-side status updates on the batch detail page; the queue has a History filter (applied + archived). Tables: `pu_vendors`, `pu_parse_profiles`, `pu_batches`, `pu_batch_files`, `pu_lines`, `p21_item_mirror` (read-only mirror, written by the sync worker via service role), `pu_exports`, `pu_item_aliases` (per-vendor match memory), `pu_settings` (single-row guardrail config). All `pu_*` PKs are `uuid`. Private Storage bucket **`price-files`** holds inbound files + generated exports.
- **Email intake (Phase 6a):** vendor emails to `priceupdate@` auto-create batches via the existing Graph webhook — `graph-notify` branches on the `clientState` queue to `createEmailBatch()` (`src/lib/emailBatch.js`, service role): dedupe on `email_message_id` (unique, upsert-ignore), **tiered vendor identification** (`identifyVendor()`: sender domain vs `pu_vendors.email_domains` → email addresses quoted in the body, which catches internal forwards from `powerandrubber.com` → a *unique* vendor-name mention in subject/body/attachment names, distinctive tokens only; tiers 2–3 record a "verify before approving" note on the batch; no confident match → Unidentified), sender/subject/body stored on the batch (shown in a batch-detail "Source email" card), attachments (xlsx/xls/csv/pdf/txt, non-inline; PDFs marked `parse_status='manual'`) → `price-files` + `pu_batch_files` + library archive under the received date, and a scoped mirror sync queues when the vendor has a supplier id. Body-only emails become fileless placeholder batches. The batch-detail Properties card has **vendor and effective-date edit controls** (pre-approval only) — changing vendor queues a scoped sync and re-runs matching; setting the effective date puts the batch on the calendar/reminders. Saving a parse profile also stores the sheet's `header_signature` in its config (the fingerprint 6b's profile recognition reads). New Graph helpers: `fetchMessageFull`/`fetchAttachments` in `src/lib/graph.js`.
- **Polish (Phase 7):** Vendors page is full CRUD — `VendorModal` covers supplier id/prefix/domains/notes/active, lists the vendor's **parse profiles** (fingerprint badge; delete clears `pu_batch_files.parse_profile_id` refs first — that FK has no ON DELETE action), and offers vendor delete only when the vendor has zero batches (`pu_batches.vendor_id` FK blocks otherwise — deactivate instead); the list shows profile/batch counts via embeds. Settings guardrails are editable (`pu_settings` id=1; changes apply at the next matching run, never retroactively). Success toasts on the batch headline actions (approve/export/applied/archive) via `src/components/Toast.js` (`useToasts` + `<Toasts>`, success-only by design — errors stay inline).
- **Auto-parse on arrival + PDF split view (Phase 6b):** after `createEmailBatch()`, graph-notify schedules `autoParseBatch()` (`src/lib/autoParse.js`, service role) via `next/server`'s `after()` — Graph gets its fast 2xx, then the batch parses + matches in the same invocation (route `maxDuration` 120). Profile selection per file: score each profile's `header_signature` against the first 20 rows of each sheet (≥0.8 wins; tolerant of vendors adding/dropping preamble rows since the header row is re-found, not pinned); no signature hit + exactly one profile → use it; otherwise the file stays `pending` for manual mapping. Lines go through the shared `applyParse` (`src/lib/priceupdatesParse.js` — client-shaped but takes any Supabase client), then matching runs via **`src/lib/matchBatch.js`** — the match core extracted from `/api/priceupdates/match` (the route now just does auth + delegates; reuse the lib for any server-side matching). Every outcome (parsed/skipped/failed file, match summary) is appended to the batch's `notes` activity. Auto-parse never marks a batch `failed`. **PDF split view:** `/priceupdates/batches/[id]/pdf?file=…` ("Enter lines" on PDF files in the batch-detail Files card) — the PDF renders in an iframe from a signed Storage URL beside a paste-friendly entry grid: pasted rows tokenize on tabs, else runs of 2+ spaces, else single spaces; first-row header auto-detected (no parseable numbers) with column auto-guess; column mapping/transforms mirror the map UI (shared `colLabel`/`guessHeaderRow`/`guessColumns`, moved into `src/lib/priceupdates.js`); Apply writes lines through the same `applyParse` + match path and marks the file `parsed` (re-applying replaces that file's lines).
- **Scheduling calendar + reminders:** the batches page has a List | Calendar toggle (persisted in localStorage). The calendar (`src/components/BatchCalendar.js`) is an Outlook-style month grid over `effective_date`: status-colored pills with a derived **readiness dot** (`batchReadiness()` — approved/exported = ready, else needs prep; never stored), a peek card on click, **drag to reschedule** (updates `effective_date`; already-archived library files keep their original date folder), click-a-day → New Batch modal with the date prefilled (`defaultEffectiveDate` prop), and an overdue/upcoming agenda panel. `attentionPill()` is effective-date-aware (overdue / load-today / due-soon-not-ready outrank the older pills) and the dashboard has a "Due to load in P21" metric. **Business dates run on Central time** — use `todayCentral()`/`daysUntil()` from `src/lib/priceupdates.js`, not raw `new Date()`. **Daily reminder digest:** Vercel cron at 12:00 UTC (7am CDT; 6am CST — cron can't track DST) → `GET/POST /api/priceupdates/reminders` (Bearer `CRON_SECRET` or logged-in `priceupdates` user; **excluded in `proxy.js`**) emails one digest per recipient of all unapplied batches with `effective_date ≤ today+7` (incl. overdue — repeats daily until applied or deleted), sent as `it@` via `sendGraphMail()`. Recipients: `pu_settings.reminder_emails` (migration `18`, editable on Settings; empty = off).
- **File library (Phase 5.5):** `/priceupdates/files` — the vendor price-file archive (browse/filter/search, upload, edit vendor/year metadata, link a file to its batch — linked files show in a batch-detail sidebar card). Filters mirror the archive hierarchy vendor → year → date: year/date are dropdowns fed by the `pu_library_facets(vendor,year)` SQL fn (migration `17`; "date" = the path segment after the year folder, since date folders exist only in storage keys); search matches file name **and** storage path. **Batches feed the library automatically:** creating a batch archives copies of its uploaded files to `library/<vendor>/<year>/<MM-DD-YY>/` (date folder from the effective date, else received date; source `batch`), and generating an export archives the `.txt` beside them (source `batch_export`, replaced on regenerate). Both are best-effort — a library failure never blocks the batch/export. Library key helpers (`slugify`/`sanitizeFileName`/`dateFolderMMDDYY`) live in `src/lib/priceupdates.js`. Objects live in `price-files` under `library/<vendor-slug>/<year>/…` (`pu_library_files` rows hold the metadata, migration `16`; **the storage key is never re-derived from metadata** — editing vendor/year just updates the row). Historical archive bulk-imports via `scripts/import-price-library.mjs` (dependency-free Node script, run on the machine holding the archive; folder-per-vendor layout, year inferred from subfolder/filename/mtime; idempotent re-runs; unmatched vendor folders import as Unassigned). `formatBytes` joined the shared helpers in `src/lib/priceupdates.js`.
- **RLS helper (reusable):** `has_app_access(app text)` = `is_agent() OR profiles.app_access ? app`. Every `pu_*` table's policy is `(select has_app_access('priceupdates'))`; the P21 mirror is user-read-only (service role writes it). Reuse `has_app_access()` for future per-app-gated tables instead of the older blanket `using(true)` — and **always wrap the call as `(select has_app_access('app')))` in policies**: the bare call gets inlined per row, which times out count queries on large tables (migration `12` fixed exactly this).

## Environment variables

App: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`.
Email/Graph: `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`, `GRAPH_CLIENT_STATE`, `IT_MAILBOX`, `PRICEUPDATE_MAILBOX`, `APP_BASE_URL` (= `https://www.prstech.app`), `HELPDESK_INBOUND_TOKEN`, `CRON_SECRET`. Optional Power Automate fallback: `POWER_AUTOMATE_NOTIFY_URL`.
P21 (Price Update Processor): **SQL replica (preferred sync source)** `P21_SQL_HOST`, `P21_SQL_PORT`, `P21_SQL_DATABASE`, `P21_SQL_USERNAME`, `P21_SQL_PASSWORD` (Epicor-provisioned `readonly_*` account), `P21_SQL_TRUST_CERT=true` (Epicor's replica presents a self-signed TLS cert since Aug 2026 — without this every connection fails cert validation; traffic is still encrypted). **OData (fallback)** `P21_BASE_URL`, `P21_USERNAME`, `P21_PASSWORD` (API service account), optional `P21_CONSUMER_KEY` (registered app `PRS-PriceUpdates`, scope `/odata`). Optional overrides (defaults confirmed against the replica): `P21_TOKEN_PATH`, `P21_TOKEN_METHOD` (POST/GET), `P21_ODATA_BASE`, `P21_SUPPLIER_VIEW` (default `p21_view_inventory_supplier`), `P21_ITEM_VIEW` (default `p21_view_inv_mast`), and field-name overrides `P21_F_ITEM_ID`/`_SUPPLIER_ID`/`_SUPPLIER_PART_NO`/`_ITEM_DESC`/`_UOM`/`_COST`/`_LIST`/`_INV_MAST_UID`/`_DELETE_FLAG`. The sync mirrors Porter's report query (join of the two views on `inv_mast_uid`, scoped per tracked supplier). The `P21_SQL_*` values (plus `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`) also live in `worker/.env` on the on-prem sync worker — that copy is the one doing real syncs.
**Never commit secrets.** Local secrets go in `.env.local` (gitignored); production in Vercel env vars; the on-prem worker's in `worker/.env` (gitignored).

## Commands

- `npm run dev` — local dev server.
- `npm run build` — production build.
- `npm run lint` — ESLint (Next flat config). Note: the codebase ships with some pre-existing lint warnings/errors; the build does not gate on them.

## Database

Migrations are plain SQL in `supabase/`, run manually in the Supabase SQL Editor **in numbered order** — see `supabase/README.md`. All are idempotent.

## Docs

`docs/` holds the transition plan, data model, build spec, deprecation checklist, and email-integration setup guides (`email-setup-graph.md` is current; `email-setup-power-automate.md` is the alternative).

## Conventions recap

- Match the existing dark-theme inline-style look (see any Help Desk page for the palette).
- Reuse `useRole`, `createClient`/`createAdminClient`, and the shared `lib/helpdesk.js` helpers rather than re-deriving.
- New tables ship with RLS on + policies. New public API routes get their own auth + a `proxy.js` matcher exclusion.
